R27 [P1] Zigzag uses the wrong ridge count, amplitude and curve geometry
Location: renderer/shapes/ZigZag.kt; renderer/Animation.kt;
format/graphicelement/modifiers/ZigZag.kt.
Cause: the old algorithm inserts twice ceil(ridges) points along the straight
chord, displaces them by half the size, leaves original corners in place, and
retains unrelated original handles. The pinned web implementation rounds the
ridge count, samples the actual cubic parameter and normal, displaces corners
too, and constructs distinct smooth handles. Zero ridges does not disable it.
Live size, ridge count and geometry were all explicitly rejected by CPU guards.
Applied fix: compute the reference cubic/normal/corner geometry in RemoteFloat.
Keyframe/easing bounds allocate up to 1024 ridge slots per segment (65536 output
vertices per contour). Unused slots collapse at endpoints without extra control
loops; active count and parity remain live. Exact zero size restores the original
cubic, including its controls. No frame sampling or raster fallback is involved.
A diagonal timing curve now returns the exact clamped progress instead of a
sample-table approximation: the latter missed the -4 to 6 zero crossing at
frame 4/10 and left zigzag enabled, visibly straightening the original curve.
Evidence: the initial ten tests all failed before implementation. Offline fixtures
are generated by executing pinned lottie-web code, not this Kotlin renderer.
They cover corner/smooth points, open/closed curves, fractional/zero ridges,
negative/zero size, degenerate paths and live size/ridge-count/geometry changes.
Broader modifier-order and post-live-boolean combinations remain under R10/R23.
Point-type follow-up: the fixed-enum parser silently replaced scalar-property
objects (including a static smooth value) with Corner after catching a decoding
exception. It now accepts both legacy numeric input and static/animated scalar
properties. RemoteFloat selectors keep corner/smooth handles live. As in the web
reference, only an exact value of 2 is smooth; interpolated fractions are not
rounded to an enum. Malformed properties fail instead of silently changing style.
Eight new native playback regressions failed before this fix and pass afterward.
They cover open/closed paths, static property-form smooth points, multi-keyframe
holds with a return to Corner, and increasing/decreasing interpolation through 2.
Five decoding/round-trip tests additionally cover defaults, legacy numbers,
static and held properties, and rejection of malformed values.
Residual tracked difference: float32 expression evaluation versus the generated
reference changes a few antialiased smooth-join edge pixels in two closed-path
motion cases. Worst whole-image red MAE is 0.000022 (0.0022%); worst single-pixel
difference is 49/255. Geometry coordinates/controls still satisfy the 0.001-unit
bound. Those two cases use a full-image mean bound of 0.00005 and an outlier bound
of 0.25; other playback tests retain their existing strict comparison. The
independent capture auditor applies these tight full-image bounds to all 220
frames. This is tracked numerical/raster variance, not claimed pixel identity.
All 27 focused playback/geometry tests pass, covering 32 static geometry cases, 20 motion cases at
11 frames each, and exact linear timing. The reference/RC review sheets were

R29 [P1] Animated polystar point counts fail; fractional geometry is misconstructed
Locations: renderer/shapes/PolyStar.kt, new PolystarTopology.kt.
Cause: point counts are required to be constant, fractional stars omit the initial
half-angle adjustment, and fractional polygons allocate ceil(points) vertices
while their angular step uses floor(points). Stars also ignore reverse direction.
Applied fix: live point-count expressions with a finite keyframe/easing capacity
bound (at most 1024 points), dynamic fractional-star start angle/radius/handles,
floor-count polygons, and live collapsed slots for unused vertices. The first
collapsed slot alone owns the closing incoming control, preventing invisible
cubic loops or extra trim length. Position, rotation, radii and roundness remain
live concurrently. Static fractional stars/polygons use the corrected geometry;
reversed stars use the reference's negative angular step. No sampled frames or
raster fallback are introduced. Negative authored counts and excessive capacity
fail explicitly; easing excursions below zero collapse the contour to a point.
Evidence: initial 12 reference comparisons had 11 failures (10 live-count guards
and one static fractional-star pixel failure); the static fractional-polygon test
passed within its original tolerance despite the redundant topology. All 12 pass
after the fix. Further comparisons cover simultaneous geometry changes, fills
and an opposite-winding hole. Six direct capacity tests cover linear motion up to
the limit, held values, increasing/decreasing overshoot and invalid bounds.
Follow-up: rounded-corner modifiers on animated polystars now retain live geometry
and topology (R31). Polygon direction currently follows lottie-android 6.7.1,
which ignores d=3 for polygons; this is not a claim of cross-player direction
parity. Broader modifier-order chains remain under R10.

fill path, including baked child-group geometry in that paint's scope. Preserve
the contour fill rule and apply opacity once. Stroke rendering and independent
repeater-opacity instances retain their existing boundaries. Trimmed paths and
non-concatenable remote operations remain separate; general live compound-trim
and mixed boolean/ordinary path batching still need implementation/coverage.
Controls cover nonzero/even-odd holes, gradient fill, 50% overlap, nested groups

R31 [P1] Baked rounded corners lose live clamps, sharpness changes and topology
Locations: renderer/shapes/RoundedCorners.kt, new LiveRoundedCorners.kt,
PolyStar.kt, Path.kt and ParametricTrim.kt.
Cause: rounded paths were evaluated at selected keyframes and interpolated after
the modifier. That misses nonlinear edge-length clamps, changing control handles
and independently timed properties. Animated polystars were explicitly rejected.
The static algorithm also clamped both sides to the shorter adjacent edge, instead
of independently limiting each side to half its own edge length.
Applied fix: evaluate corner splitting in RemoteFloat at playback time, with exact
zero-handle sharpness checks, independently clamped adjacent edges, protected open
endpoints and safe zero-length edges. Each source vertex has two recorded slots;
non-rounded pairs collapse while preserving original incoming/outgoing controls.
Animated polystars pass their logical active vertex count so padding is not treated
as extra corners, and the closing control is transferred exactly once. The sampled
rounded-keyframe synthesis was removed. Rounded single-contour paths with trim use
native playback trimming. No raster fallback or temporal sampling was added.
Evidence: all 10 initial reference-generated playback repros failed before this
implementation. Nine passed immediately; the tenth compared native trim with the
old precomputed trim fixture. The explicit reference path now uses native trim too
(zero-radius bypass, no reference rounding), and separate Android comparisons
cover radius changes, moving rounded paths and animated trims. Other comparisons
cover intrinsic star/polygon roundness preserving existing controls during changing
point counts. Rounding coordinates are generated offline by pinned lottie-web;
polystar source vertices are independently computed analytic geometry, not Kotlin
renderer outputs. Every playback case uses one mounted document for all frames.
Compound-evaluator follow-up: evaluatePathGeometry still had a separate branch
rejecting rounded multi-contour trims after the shared trim evaluator gained
compound arc-length support. Three analytic regressions reproduced that rejection.
The applied fix routes rounded geometry through trimEvaluatedPaths (playback=true),
preserving native single-contour trimming and sharing compound length/clamping.
The regressions use two equal-length, independently specified rounded L contours:
0..50% and 50..100% retain the respective whole contour and its control handles;
25..75% cuts each rounded arc at its analytic symmetry point.
A player test drives a named end percentage forward and backward through
0/25/50/75/100, checking contour visibility and endpoints without rerecording.
This fixes the legacy evaluator restriction; the authored modifier pipeline
already used the common trim policy. Arbitrary modifier-chain ordering and
nonlinear modifiers after a live boolean still require implementation under
R10/R23. This does not close the full task list.

R32 [P1] Later geometry modifiers leave already-emitted paints unchanged
Location: renderer/Shape.kt, gatherShapes.
Reproduction: [square path, fill or stroke, animated pucker/bloat]. The visible
paint stays square while an equivalent modifier before the paint animates.
Zigzag, twist and offset have the same paint-scope error. A preceding styled
group is ignored when no direct geometry remains. Unstyled group geometry is
also omitted from the modifier's input before a following inherited paint.
Cause: modifier branches replace only currentGeometries; shapeGroups already
hold immutable earlier path values. Rebuilding RepeatedShapeInstance with its
default multiplier also resets opacity supplied by a preceding repeater.
Applied fix: pointwise modifiers update prior styled views, current geometry
instances, and unstyled group geometry. Preserve each paint, group transform,
group opacity, and repeated instance multiplier. Hidden modifiers are no-ops;
later siblings are outside the modifier's scope. Each view is updated once,
including chains with a paint between two modifiers.
Evidence: ModifierPaintScopeTest contains 15 native playback cases, each with
11 frames on one mounted live document: fill, stroke, both gradient paints,
multiple paints, two modifiers spanning paints, hidden modifier, later sibling,
earlier paints across a geometry reset, styled/transformed group, inherited
paint, repeater opacity, offset, twist, and zigzag. Thirteen valid pre-fix
cases failed pixel comparisons; the hidden control passed and the repeater
fixture first needed a missing JSON brace corrected. All 15 pass after fixing
the renderer. Pucker references use analytic vertex/control radii (including
two composed modifiers), offset uses an analytic expanded square, twist uses
the branch's distance-weighted polar-coordinate contract, and zigzag uses the
pinned web geometry fixture. No production modifiers compute expected paths.
tools/check_modifier_scope.py audits full RGB captures and produces review
sheets; it checks all 165 frame pairs, dimensions, visible reference content,
mean error and peak error. This is not a claim of arbitrary modifier-chain or
After Effects twist parity. Merge operations need operand aggregation rather
than pointwise mapping; trim/rounding order, nonlinear modifiers after live

R02 [P1] Fractional and zero-duration easing segments produce incorrect values
Location: renderer/Animation.kt, lookupValueInBezier.
Origin: present in comparison main.
Reproduction: linear handles (0,0,1,1), duration=0.5, frame=0.25 should produce
0.5; at frame=0.5 or later it should produce 1. The old code returns 0 for all
three. A duration of 2.5 ends at 0.8 rather than 1. A zero-duration segment
produces a non-finite result (constantValue evaluation throws).
Cause: sampling 0..duration.toInt(), dividing by duration, then truncating a
floating-point array index. The fractional endpoint is never sampled, and
intermediate frames are rounded down. Coincident keyframes divide by zero.
Suggested/applied fix: sample a normalized interval including both endpoints;
interpolate adjacent samples and clamp lookup positions. Zero-length segments
choose the later endpoint. The table is bounded to 32..4096 intervals to avoid
allocations proportional to arbitrarily large durations.
Evidence: failing subframe/zero-duration regressions, then passing endpoint and
clamping tests. Easing remains a sampled approximation, not an exact runtime
cubic solver; extreme easing curves need additional accuracy testing upstream.

R04 [P1] Animated mask and matte geometry loses every dynamic coordinate
Location: renderer/Shape.kt, buildRemotePathFromBezier/applyLayerMasks/clipShapes.
Origin: branch implementation. Status: fixed with native playback pixel tests.
Cause before fix: every vertex and tangent read constantValueOrNull ?: 0f. Normal playback
uses a dynamic RemoteFloat frame, so animateBezier can return expressions even
when an equivalent isolated constant-frame test succeeds. A mask path then
collapses toward (0,0), hiding content or revealing too much.
Minimal reproduction: solid layer with an add mask whose rectangle moves from
x=0 to x=50; play one compiled document through a named progress variable.
Compare against captures of independently evaluated constant frames.
Suggested/applied fix: build clipping paths with the same expression-aware path builder
used by RemoteLottiePath.draw, preserving RemoteFloat dependencies. Add a
single-document playback test, not only constant-frame geometry assertions.
Evidence: PlaybackEffectsRegressionTest failed its initial red probe before
the fix, then verified static masks and an animated rectangular add mask at
frames 0, 5, and 10 in one document. The shared clipping helper also preserves
matte path coordinates; this does not implement the missing matte semantics
in R05 or mask compositing in R06.

R05 [P1] Track mattes use intersected outlines instead of rendered alpha/luma
Location: renderer/Shape.kt, applyMatteClip and clipShapes.
Origin: branch implementation. Status: code-confirmed.
Cause: positive matte shapes call clipPath(Intersect) one by one. Two disjoint
filled shapes therefore yield an empty intersection rather than their union.
Luma and alpha modes take the same clipping path; fill color, opacity, matte
timeline visibility, and masks do not contribute. Image/text mattes take the
empty else branch. Layer.kt does not pass matteContext to PrecompLayer at all.
Minimal reproductions: two disjoint opaque rectangles in a shape matte; a black
solid luma matte over a colored target; a precomp target with an alpha matte;
a matte whose op precedes the target op.
Suggested fix: composite the rendered matte into an alpha/luminance surface
with the correct mode and time, then apply it to every target layer type. A
union of paths only fixes the disjoint-shape case; it is not full matte support.

R06 [P1] Masks ignore opacity/expansion and reorder mixed operations
Location: renderer/Shape.kt, applyLayerMasks; format/mask/Mask.kt.
Origin: branch masking implementation. Status: code-confirmed.
Cause: mask opacity never reaches rendering; expansion is absent from the model.
Non-inverted add masks
are collected and intersected at the end; subtract/intersect masks execute
earlier regardless of authored order. Difference is treated as subtraction.
Minimal reproductions: an add mask with opacity=0; a mask with expansion=10;
subtract followed by add on overlapping shapes. Inspect output against the
reference renderer, including inversion and half-opacity cases.
Suggested fix: evaluate ordered mask compositing with alpha, expansion, and
mode semantics. Hard clipping alone cannot implement partially opaque masks.

R07 [P1] Precomp transforms use child time and precomp masks are dropped
Location: renderer/layers/Layer.kt, Precomposition branch; PrecompLayer.kt.
Origin: branch implementation. Status: timing fixed; masks/bounds remain unfixed.
Cause before timing fix: Layer switches currentFrame to remapped/stretched local time before
PrecompLayer appends the precomp transform to the child's stack. All stack
transforms are later evaluated using that child's frame. A precomp's own
animated transform belongs to its containing composition's timeline. Further
nested precomps can incorrectly retime outer transforms again. The precomp's
masks are never applied, and its width/height do not establish clipping bounds.
Minimal reproduction: precomp with st=10, animated outer translation, and a
static child; render parent frame 20. Add a mask to the precomp layer. Repeat
with time remap and a nested precomp.
Applied timing fix: bind the outer transform stack to RemoteFloat expressions
using its containing timeline before switching to child time. Static property
wrappers hold these dynamic expressions without evaluating them a second time
against a nested child's timeline. This is not a frame-zero snapshot.
Evidence: failing native playback tests now cover st=10/sr=2, nested precomps,
time remap in seconds, and an animated root parent; an unshifted control remains
correct. A second progress update verifies the bound transform keeps moving.
Remaining suggested fix: apply layer masks and bounds around the rendered
precomp, not separately to child geometry. These were intentionally not changed.

R08 [P1] Text layers without vector glyphs render nothing; text changes freeze
Location: renderer/layers/TextLayer.kt, TextLayer.
Origin: branch implementation. Status: code-confirmed.
Cause: the only drawing branch is if (charsMap.isNotEmpty()). There is no font
text drawing fallback. TextDocument selection uses currentFrame.constantValueOrNull
?: 0f, so dynamic playback selects frame-zero text forever. Missing characters
also vanish without advancing the cursor; fallback glyph lookup may choose a
different family/style.
Minimal reproductions: a text layer with a fonts list and no chars; two text
documents at t=0 and t=30 in a document driven by named progress.
Suggested fix: implement a font-backed text path or explicitly reject unsupported
font text, plus runtime document selection and correct font/glyph lookup. Keep
font-text, glyph-text, missing-glyph, and animated-document tests separate.

R09 [P1] Several geometry modifiers only work for constant-frame evaluation
Location: renderer/shapes/{PolyStar,ZigZag,PuckerBloat,Twist,OffsetPath,MergePaths}.kt;
Rectangle.kt and Ellipse.kt when trim/rounding is present.
Origin: branch geometry implementation. Status: rectangle/ellipse trim and
rounding fixed; other modifier paths remain code-confirmed follow-ups.
Cause: animated property results or vertices are converted using
constantValueOrNull ?: 0f. Animated polystar points/radius can become zero;
animated twist/offset/zigzag parameters become no-ops. Boolean merge paths turn
dynamic points into zeros. Adding a trim or rounding modifier to a moving
rectangle/ellipse previously converted its dynamic geometry into a static
zero-valued path.
Minimal reproductions: animate polystar radius; animate a rectangle's position
and add an otherwise neutral trim (0..100%); merge two moving paths. Drive all
examples through the same compiled document rather than recording a new one
per frame.
Applied parametric fix: retain rectangle/ellipse coordinate expressions. Apply
rectangle rounding analytically (its own radius wins over the modifier), and
use the player's live path measurement for dynamic geometry trimming. Constant
geometry with constant trim values keeps the existing precomputed trim path.
R41 also moves authored paths and animated trims on static parametric shapes to
native live measurement, removing synthetic trimmed keyframes. Ellipses have no sharp
corners for the rounding modifier to replace.
Evidence: eleven native playback tests cover translation, resizing, full and
half trim, rounding, animated radius, and animated trim endpoints. Static
reference fixtures are explicitly remounted per frame and independently probed
for their expected position; the dynamic document is never remounted.
Remaining suggested fix: use remote expressions where topology permits; for
topology or boolean operations, precompute geometry with an explicit sampling
strategy or provide player-side support. Never silently replace expressions
with zero.
Boolean merges and the other listed modifiers were not implemented here.
Combined multi-contour trims and interactions with later baked nonuniform
geometry transforms still need reference-parity coverage; wrapped runtime trims
draw two segments and may expose stroke-cap seams at the contour boundary.

R10 [P1] Repeater copies, opacity, and animated scaling are incomplete
Location: format/graphicelement/modifiers/Repeater.kt;
renderer/shapes/Repeater.kt, evaluateRepeater/transformRepeaterBezierValue;
renderer/Shape.kt, gatherShapes.
Origin: branch implementation/port. Status: standard decoding, styled-content
repetition and start/end opacity fixed; broader repeater behavior remains open.
Cause before fix: repeater tr is a generic Transform and cannot retain start/end opacity
so/eo. It also requires ordinary o, so a tr containing so/eo without o fails
decoding instead of using repeater opacity. When o is supplied, rendering sets
endOpacity=startOpacity from o. Exported [geometry,fill,repeater] ordering also
left the already-emitted fill untouched, drawing a single unmodified original.
Dynamic counts still default to one and offsets to zero.
For dynamic scale and copy index k>1, scale^k becomes just scale. Preceding
groups were previously excluded from repetition; interactions with a following
fill and nested group transforms still need reference-parity coverage.
Minimal reproductions: three copies, so=100/eo=0; 2.5 copies; an animated scale
with at least three copies; place a group before a repeater and a fill.
Applied fix: a repeater-specific transform model retains so/eo without requiring
ordinary o. Missing endpoints default to 100%; legacy o supplies only missing
endpoints for compatibility. Repeat already-styled content as a unit, scaling
the opacity inherited by its paints rather than leaving an unmodified original.
Use copyIndex/copies for the ramp (not copyIndex/(copies-1)). For 2.5 copies the
pinned reference draws two copies, with ramp factors 0 and 0.4; truncation alone
is therefore not a parity defect against that reference.
Evidence: six initial native tests failed decoding, then failed pixel checks
after parser repair, then passed for zero/one/three copies, constant and animated
ramps, and fully transparent endpoints. Four additional passing controls cover
omitted endpoints, legacy opacity, explicit endpoint precedence, and fractional
copy counts. Broader parent/group transform ordering, dynamic counts/offsets,
exponential animated scaling, and opacity through later modifiers still need
implementation and reference-parity tests.
Reference contract (the dependency version used by this module):
https://github.com/airbnb/lottie-android/blob/v6.7.1/lottie/src/main/java/com/airbnb/lottie/animation/content/RepeaterContent.java

R11 [P1] Gradient alpha stops are matched by index rather than position
Location: renderer/RemoteStyle.kt, extractGradientColorsAndPositions;
format/properties/Gradient.kt, gradient property serializers.
Origin: branch implementation. Status: fixed with native playback pixel tests.
Cause before fix: equal numbers of color and alpha stops bypass position interpolation.
Otherwise sampleAlpha can only compare constant positions and falls back to
the first alpha for dynamic values. Output stops are emitted only at color
positions, so an opacity breakpoint between color stops disappears.
Minimal reproductions: two color stops at 0 and 1, three alpha stops at
(0,1),(0.5,0),(1,1): the center should be transparent but is opaque. Also use
three color stops at 0,0.5,1 and three alpha stops at 0,0.25,1, with differing
alpha values; equal counts do not imply corresponding positions.
Suggested/applied fix: merge color/alpha positions and interpolate both channels
at the combined stops. Preserve dynamic offsets with RemoteFloat expressions
and stable runtime sorting when alpha stops cross RGB stops. Retain coincident
RGB hard stops and pad a one-color shader to the platform's two-stop minimum.
Prerequisite parsing defects found by the reproductions: custom descriptors
requested nonexistent serializers for RemoteBoolean and GradientValue, and
animated dispatch ignored a=1 inside standard g={p,k:{a,k}}. Use explicit
descriptors and select the nested property's discriminator while retaining p.
Evidence: tests first failed during decoding, then reproduced opaque centers
and misplaced alpha breakpoints after the parser fix. Pixel tests cover unequal
counts, equal counts/different positions, changing alpha values, a moving alpha
stop crossing and coinciding with an RGB stop, no-alpha and one-color controls,
and coincident RGB hard stops with/without transparency. No comparison-renderer
parity claim is made for every exporter variant or arbitrary gradient topology.

R13 [P1] Per-dimension easing and spatial position curves are lost
Location: format/values/KeyframeEasing.kt, parseTangentValue;
format/properties/Position.kt; renderer/properties/{Vector,Position}.kt.
Origin: comparison-main property model/evaluators. Status: fixed with playback
and serialization regressions.
Cause before fix: easing arrays retain only their first entry, and the same timing factor
is applied to every dimension. PositionPropertyKeyframe retains spatial to/ti
tangents, but animatePosition ignores them and follows a straight line between
endpoints.
Minimal reproduction: vector with different x/y easing handles; a position
segment whose spatial control points bend away from its endpoint chord.
Suggested/applied fix: preserve per-dimension easing arrays in both decoding and
encoding, select vector/position-axis handles independently, and traverse spatial
cubics by eased arc length. Both spatial tangents belong to the starting keyframe,
with incoming relative to the endpoint. Bounded 256-interval length and position
tables retain dynamic playback; overshoot extrapolates along endpoint tangents.
This is a sampled approximation, not an exact cubic arc-length solver.
Evidence: fourteen native tests cover curved midpoint/endpoints, independent
Android PathMeasure quarter-frame checks on an asymmetric curve, holds, linear
controls, scalar/singleton easing fallback, serialization round trips, independent
axis easing, and spatial over/undershoot. The focused property suite passed 146
tests. Extreme coordinate magnitudes and unusual curve shapes need further
accuracy coverage upstream; separated-dimension position objects remain outside
this change.
Reference for arc-length traversal and overshoot:
https://github.com/airbnb/lottie-android/blob/v6.7.1/lottie/src/main/java/com/airbnb/lottie/animation/keyframe/PathKeyframeAnimation.java

R15 [P2] Several parsed or declared layer features are silently ignored
Location: format/layer/{Layer,ShapeLayer,SolidColorLayer,NullLayer}.kt;

R16 [P2] Layer endpoint padding conflicts with its half-open visibility contract
Location: LottieAnimation.kt, frame calculation;
renderer/layers/Layer.kt, calculateEffectiveEndFrame.
Origin: branch visibility behavior. Status: code-confirmed.
Cause: progress=1 maps exactly to composition op, then matching layer op is
extended by 0.01 to retain visibility. Visibility therefore depends on root op
rather than solely on the layer's [ip,op) interval. The epsilon can disappear
at large frame values. Child precomps inherit the outer endFrame unchanged.
Minimal reproduction: sample exactly at layer op with and without a longer
root op; repeat inside a shifted/stretched precomp.
Suggested fix: define the public progress endpoint policy at the root and keep
layer out-points exclusive. Pass correct child composition bounds. Account for
existing progress=1 callers and screenshot expectations when changing this.

R17 [P2] Degenerate input reaches unchecked arithmetic and indexing
Location: format/Animation.kt; LottieAnimation.kt;
renderer/properties/Vector.kt; renderer/Transform.kt.
Origin: mixed comparison-main and branch behavior. Status: code-confirmed.
Cause: default root width/height and endFrame are zero, but rendering divides
by dimensions and takes clock modulo (op-ip). An animated vector with k=[]
indexes keyframes[0]; transform scale assumes at least two components.
Minimal reproductions: decode {} and attempt playback; evaluate {"a":1,"k":[]}
as a vector; use an undersized scale vector. These are resilience cases, not
claims that the malformed inputs are valid Lottie documents.
Suggested fix: validate root dimensions/timeline before recording, and establish
consistent rejection or fallback policies for malformed properties. Prefer a
clear load error to non-finite expressions or an incidental index exception.

R18 [P2] Passing tests do not establish reference-renderer parity
